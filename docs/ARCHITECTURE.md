# Architecture

How the PostgreSQL platform plugs into Nextcloud Full Text Search, and why it is built the way it is.

## Where it sits

```
 Content providers                 Full Text Search app               This app
 (Files, Deck, Bookmarks…)  ──►   (queues, locking, occ,      ──►   PostgreSQLPlatform
  produce IIndexDocument           unified search UI)                implements IFullTextSearchPlatform
                                                                          │
                                                                          ▼
                                                              Nextcloud's own PostgreSQL DB
                                                              table ftspg_<prefix>index
```

The framework calls the platform through `OCP\FullTextSearch\IFullTextSearchPlatform`:

| Method | What happens here |
|---|---|
| `loadPlatform()` | Creates the table if it is missing. |
| `testPlatform()` | Checks the database is PostgreSQL and the schema is in place. |
| `initializeIndex()` | Creates table and indexes (idempotent). |
| `indexDocument()` | Extracts text, then upserts one row. Reports warnings to the runner. |
| `deleteIndexes()` | Deletes rows. |
| `resetIndex($provider)` | Deletes a provider's rows; `all` truncates the table. |
| `searchRequest()` | Runs a search for one provider and fills the `ISearchResult`. |
| `getDocument()` | Rebuilds an `IIndexDocument` from a row (used by `occ fulltextsearch:document:platform` and `occ fulltextsearch:test`). |

## The table

```sql
CREATE TABLE ftspg_oc_index (
  id            bigserial PRIMARY KEY,
  provider_id   varchar(64)  NOT NULL,
  document_id   varchar(254) NOT NULL,
  owner_id      varchar(64)  NOT NULL DEFAULT '',
  access        text[]       NOT NULL DEFAULT '{}',   -- u:alice, g:sales, c:<circle>, u:__all
  links         text[]       NOT NULL DEFAULT '{}',
  tags, metatags, subtags     text[],
  source, hash, modified_time, indexed_at,
  config        regconfig    NOT NULL,                -- language the row was indexed with
  title, tags_text, parts (jsonb), parts_text, content, info (jsonb),
  tsv tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector(config, title),      'A')
     || setweight(to_tsvector(config, split(title)), 'A')   -- file name parts, see below
     || setweight(to_tsvector(config, tags_text),  'B')
     || setweight(to_tsvector(config, parts_text), 'C')
     || setweight(to_tsvector(config, content),    'D')
  ) STORED,
  UNIQUE (provider_id, document_id)
);
-- GIN indexes on tsv, access, metatags, subtags; trigram GIN index on title when pg_trgm exists
```

  title_search text GENERATED ALWAYS AS (lower(title)) STORED,   -- for substring and typo matching

(For Turkish rows each column is first passed through `translate(col, 'Iİ', 'ıi')`; see below.)

### File names

PostgreSQL's text parser reads `rapor_2025_final.pdf` as a single "host" token, so `final` or `2025` would never match it. The title is therefore indexed twice: as written, and with `regexp_replace` splitting it at punctuation (`_ . - / + ~ , ; : ( ) [ ] { }`) and at letter/digit boundaries (`IMG20250412` → `IMG 20250412`). `TsQueryBuilder` splits search words the same way and matches either the whole word or its parts in sequence. The whole form keeps host names and e-mail addresses in document text searchable.

### Schema versions

The generated columns' definition version is stored as a comment on `tsv` (`ftspg schema 2`). When the repair step or `loadPlatform()` finds an older marker, it drops and re-adds the generated columns, and PostgreSQL recomputes them for every row. That rewrite locks the table while it runs; on large indexes, upgrade during a quiet period.

### Why raw SQL and an unprefixed table name

Nextcloud manages schemas through Doctrine, and Doctrine has no mapping for `tsvector`, `text[]` or `regconfig`. Nextcloud introspects **every** table that starts with its table prefix whenever any app runs a migration. A prefixed table with these columns would make all of those migrations fail with *"Unknown database type tsvector requested"*.

So the table is created with raw SQL by a repair step and named `ftspg_` + prefix + `index`, which Nextcloud's schema filter skips. The app also drops `oc_fts_pgsql_index`, the table version 1.0.0 tried to create, for the same reason.

### Why a generated column

The search vector is always consistent with the stored text, a single `INSERT … ON CONFLICT DO UPDATE` writes a document atomically, and weights come for free. Storing `config` per row keeps old rows valid if the language setting changes, until they are reindexed, and lets each document carry its own language when several are configured.

### Several languages

`IndexService` asks `LanguageDetector` for the language whenever content is indexed, and leaves `config` unchanged on metadata-only updates. The detector runs one statement: `ts_debug(cfg, sample)` for each configured `cfg` over the first 2,000 characters, counting word tokens whose dictionary returned no lexeme (stop words). The winner needs at least 2 and 1.5× the runner-up; otherwise the first language is used.

`SearchService` compiles the query once per language with `TsQueryBuilder` and ORs the branches, each guarded by the rows' language: `d.config = 'english' AND d.tsv @@ to_tsquery('english', …)`; the first language's branch takes `d.config <> ALL (other languages)`, which includes rows indexed in a language no longer configured. Rank queries are computed once in the `q` CTE and picked per row with a `CASE` on `d.config`, which also feeds `ts_headline`. Each branch is a GIN-indexable `@@`, so PostgreSQL combines them with a BitmapOr. With one language the SQL is the same as before.

## Indexing

1. The framework hands over an `IIndexDocument` whose `IIndex` status says what changed.
2. If only metadata changed (`INDEX_META` without `INDEX_CONTENT`), the stored content and parts are kept: a new share does not wipe the text.
3. Otherwise `ContentExtractor` produces text:
   - not encoded → used as is (HTML tags stripped if present);
   - base64 → decoded, then by magic bytes: `%PDF-` → `pdftotext`, or the bundled parser when it is missing or fails (`pdf_extractor`), with size and `memory_limit` guards and its PHP warnings kept out of the log; `PK\x03\x04` → zip, reading `content.xml` (ODF) or `word/*.xml`, `xl/sharedStrings.xml`, `ppt/slides/*.xml` (OOXML); text-like → UTF-8 / UTF-16 / Windows-1254; other binaries → no content plus a warning.
   - Result is valid UTF-8, has no NUL bytes, whitespace is collapsed, and it is cut to `max_content_size` bytes on a character boundary.
4. One upsert writes the row. If it fails while content is present (typically the 1 MB `tsvector` limit), it is retried without content so the document stays findable by title, and the runner gets a warning.

## Access control

Document access becomes an array of tokens: the owner and shared users as `u:<uid>`, groups as `g:<gid>`, circles as `c:<id>`, and `u:__all` for public documents. At search time the framework passes an `IDocumentAccess` with the viewer's id, groups and circles, which becomes the same kind of tokens. A row is visible when the arrays overlap:

```sql
WHERE d.access && '{u:alice,u:__all,g:sales,c:team1}'::text[]
```

That is a single GIN-indexed test. Share links are stored for `getDocument()` but never grant search access. An empty viewer id returns no results.

## Searching

`TsQueryBuilder` follows the framework's query contract (verified by `occ fulltextsearch:test`):

| Input | Meaning | tsquery |
|---|---|---|
| `word` | optional, prefix | `to_tsquery(cfg, '''word'':*')` |
| `+word` | required, prefix | same, ANDed |
| `-word` | excluded, exact | `!! to_tsquery(cfg, '''word''')` |
| `"a b"` / `+"a b"` / `-"a b"` | phrase | `phraseto_tsquery(cfg, 'a b')` |

User text is always a bound parameter and quoted as a tsquery literal, so neither SQL nor tsquery operators can be injected. Three expressions are built:

- **match**: required terms ANDed (or, if there are none, optional terms ORed), minus exclusions;
- **rank**: every positive term, for `ts_rank_cd`, and each positive term on its own for IDF weighting (below);
- **all**: every positive term ANDed. Rows matching it sort first, so precise matches are never buried under partial ones.

The query pages inside a subquery and computes `count(*) OVER ()` for the total; `ts_headline` then runs only on the returned page. Excerpts are plain text (no markup), split into fragments.

### Query planning

The index table's heap is small: titles, arrays and pointers, with every body and search vector stored out of line (TOAST). PostgreSQL's cost model sees a cheap heap, charges almost nothing for evaluating `tsv @@ query` on a row (for a TOASTed vector it means fetching and decompressing it), and overestimates GIN scans. After `ANALYZE` it therefore preferred reading every row the user may see, sequentially or through the access index, and testing each vector: 1.3 s instead of 0.3 s for 12,000 matches among 90,000 visible documents on 100,000, 61 ms instead of 8 ms on 4,000.

Each search now picks where it starts:

- **From the full-text index** (the usual case). Every filter (provider, access, tags, `since`, regex/wildcard) is written as `(condition) IS TRUE`: the same rows, but no index can serve it, so the GIN index is the only way in. Filters then run on the small heap row, which is cheap.
- **From the filters**, when the planner estimates they select fewer than a tenth as many rows as the words, as for a provider with a few documents or a user with few files: testing those few vectors beats visiting every document that contains a common word (160 ms instead of 640 ms for 40 documents against 90,000 with the word). The match condition is then written as `IS TRUE` instead.

Both estimates are planning-only `EXPLAIN`s, about a millisecond each. The search's statements run in a transaction of their own with `SET LOCAL` settings that keep the planner from working around the chosen index: `enable_seqscan` off (a sequential scan stays possible as a last resort), `random_page_cost` at most 1.1 (the usual value for SSDs instead of 4 for spinning disks; a server configured lower keeps its value), and `jit` off (before PostgreSQL 18, a disabled plan type adds a huge constant to plan costs, enough to trigger JIT compilation). Inside a caller's transaction the previous values are restored afterwards. Tests replay the search's own statements with `EXPLAIN` to check which index each plan starts from.

### Excerpts

`ts_headline` tokenizes all the text it is given: 70–90 ms for a 500 KB document, so a page of long results spent over a second on excerpts alone. Bodies over 10,000 bytes are excerpted from a 10,000-character window starting 500 characters before the first match. The first match is the earliest position, in the lowercased body, of any search word as typed or any lexeme of the row's tsquery (stems, accent variants, typo corrections, read from `querytree()`), preferring a word start; stems usually begin their surface forms. Without a match (a title-only hit) the window starts at the beginning, as `ts_headline` would show anyway. A long body is detoasted once into a subquery column, and `octet_length()` decides "long" from the stored size without decompressing; `OFFSET 0` keeps PostgreSQL from inlining those subqueries and repeating the work at each use. On 20 results of 550 KB, excerpts take 280 ms instead of 1.5 s.

For Turkish rows, `ts_headline` sees the text with `I→ı`, `İ→i` applied, like the indexed vector, otherwise `ISPARTA` would lowercase to `isparta` and never match. Each fragment is then copied back from the original text at the same position (the mapping is one character for one character), so excerpts show the text as written.

### Filters and limited fields

The Files app's search options arrive as request fields, interpreted as the Elasticsearch platform does:

- **Regex and wildcard filters** (*filter by extension* is the regex group `[['title' => '.*\.pdf']]`): entries of a group are ORed, groups are ANDed, and a pattern must match the whole `title` or `content`, ignoring case (`~*` with `^(?:…)$`; wildcards `*` and `?` become `ILIKE`). A regex that PCRE rejects, or that uses constructs PostgreSQL reads differently (`\K`, `\Q…\E`, `\b`, named or atomic groups, inline flags, possessive quantifiers), matches nothing instead of failing the statement. So does a field without a column.
- **Limit fields** (*search in file name / content*): `title`, `tags`, `parts.*` and `content` map to the vector weights A, B, C and D. Words carry them as tsquery weights (`'rapor':*A`), still served by the GIN index with a recheck; phrases, which `phraseto_tsquery` cannot label, are rechecked against `ts_filter(tsv, '{a}')`; exclusions only exclude within the limited fields. Title substring and title similarity matching only run when titles are searched. A limit naming no indexed field finds nothing.

### Ranking several words by rarity

`ts_rank_cd` counts occurrences and weights them by field (title A, tags B, parts C, body D), but it has no idea how common a word is. In `invoice kırklareli`, a document mentioning *invoice* twice in its body outranks the one document mentioning *Kırklareli* once, although nearly every document says *invoice*. With two to eight positive terms (words or phrases), each one is scored separately and weighted by BM25's inverse document frequency:

```
idf_i = ln(1 + (N - df_i + 0.5) / (df_i + 0.5))
rank  = Σ idf_i · ts_rank_cd(tsv, term_i, 32) / Σ idf_i
```

Normalisation 32 maps each term's weighted occurrence count *c* to *c* / (*c* + 1), a saturating term frequency like BM25's, and the weighted mean keeps `rank` between 0 and 1. Rows containing every term still sort first (`all_match`); the IDF rank orders within that group and among partial matches. Field weights still apply inside each term's score, so a common word in a title can still beat a rare word in body text, as it would with BM25F.

**Frequencies.** Before the search, one statement counts each term's documents with its own subquery: the term's `@@` in each language branch plus the search filters (provider, access tokens, tags, `since`). The GIN indexes answer those conditions exactly, so rows are counted without reading their tsvector; one scan with a `FILTER` per term would detoast every match once per term, six times slower on long documents. Only documents the viewer can open are counted, so ranking reveals nothing about other users' documents.

- Counting stops at 10,000 matches. For a term that common, the planner's estimate (`EXPLAIN (FORMAT JSON)` of the same subquery) is used instead: `ANALYZE` keeps statistics on the most common lexemes, so the estimate is within a few percent for frequent words, and exact counts are spent on rare words, where they matter.
- **N** is `pg_class.reltuples` for the index table, or an exact `count(*)` below 10,000 rows. Counting the viewer's visible documents on every keystroke would cost more than the search. When df is much smaller than N, the difference between two weights is ln(df_j / df_i) whatever N is, so the estimate barely matters; `max(N, df)` keeps the logarithm defined if statistics are stale.
- A term no visible document contains (a stopword, an unknown word) gets no weight. If fewer than two terms remain, or there is one positive term or more than eight, the single `ts_rank_cd` over the whole query is used, exactly as before: with one term IDF cannot change the order.
- Typo alternatives and accent variants are part of their word's tsquery, so they count towards that word's frequency.

The weights are bound into the search as numbers rather than computed in a CTE of the same statement: a second reference to the `q` CTE would materialise it and rule out the parallel scan PostgreSQL uses for large result sets.

**Query shape.** Each extra term costs one more `ts_rank_cd` per matching row. Costed into the scan, that makes PostgreSQL prefer a parallel sequential scan even for a few thousand matches, which tests every row's tsvector and is slower than the bitmap scan of the GIN index. So when the terms' frequencies add up to less than a quarter of the index, the matching scan sits in an `OFFSET 0` subquery that is planned as before, and ranking happens above it. Above that share, PostgreSQL scans in parallel anyway, as it did before, and the unfenced query lets the workers rank.

**Cost**, measured on 100,000 synthetic documents (300 words each, every 20th 8,000 words) with PostgreSQL 16, median of 5:

| Search | Matches | Before | After |
|---|---|---|---|
| one word | 195 / 90,000 | 10 ms / 1.5 s | unchanged |
| two words, mid frequency | 9,000–12,000 | 140–215 ms | 175–320 ms |
| three words, mid frequency | 7,000 | 115 ms | 150–210 ms |
| two or three words, one in 90% of documents | 90,000 | 1.2–1.5 s | 1.3–1.7 s |

On instances where searches match a few hundred documents, the difference is a few milliseconds.

With `pg_trgm` available, each plain search word of three or more characters can also be satisfied by `title_search LIKE '%word%'`, served by the trigram index. The planner combines it with the `tsv` index in one bitmap scan. Stopwords are excluded with `numnode(to_tsquery(…)) > 0`, which PostgreSQL evaluates once at planning time. Substring-only matches have no full-text rank, so they sort after real word matches.

If page 1 has no results and `pg_trgm` is available, titles are searched with `word_similarity` (`<%`, GIN-indexed) for typo tolerance.

## Typo correction

A second table, `ftspg_<prefix>words`, holds every distinct word in the index: lowercase surface forms (the `simple` text search configuration, so no stemming), letters only, 3–40 characters. It has a `folded` generated column with accents removed (`çalışma` → `calisma`, via `translate()` with the same character lists as `Tools\Fold` in PHP), b-tree indexes in the `C` collation so `LIKE 'prefix%'` is indexed, and a trigram index on `folded` when `pg_trgm` exists.

**Maintenance.** After each document is stored, one `INSERT … SELECT … ON CONFLICT DO NOTHING` adds its words, computed inside PostgreSQL and inserted in sorted order so concurrent indexers cannot deadlock. Words are never removed one by one; `occ fulltextsearch_pgsql:vocabulary --rebuild` recreates the table in batches, and `resetIndex('all')` empties it.

**At search time**, for each plain positive word (exclusions and phrases are left alone):

1. *Accent variants*: vocabulary words with the same folded form, or for 4+ letters the same folded prefix, that don't already start with what was typed. Shortest first, skipping words covered by a shorter variant, at most three.
2. *Spelling corrections*, only when the word has no accent variants and no vocabulary word starts with it (so it matches nothing as typed) and it has 4+ letters: trigram similarity on `folded` (threshold 0.2, set for the lookup and reset after) shortlists 20 candidates within ±1–2 letters of length. An optimal-string-alignment edit distance, where swapping adjacent letters counts as one edit, keeps those within 1 edit (2 for 7+ letters). Only the closest ones are kept, at most two.

Alternatives are ORed into the word's tsquery as prefix terms (`('rpaor':*) | ('rapor':*)`), so they count towards "all words" ranking and required `+words`, and the original word still matches.

The vocabulary is instance-wide, including words from documents a user cannot open. Alternatives only widen a query that is still filtered by access control, and they are never shown, so results never include inaccessible documents.

## Turkish dotted and dotless I

PostgreSQL lowercases with the database's `LC_CTYPE`. Unless that is `tr_TR`, `I` lowercases to `i`, which is wrong for Turkish (`ı`), so `ISPARTA` would index as `isparta` while users type `ısparta`, and uppercase text would miss its lowercase forms. For rows with the `turkish` configuration the generated column applies `translate(text, 'Iİ', 'ıi')` before `to_tsvector`, and `TsQueryBuilder` applies the same mapping to the query. Both sides agree regardless of the database locale.
