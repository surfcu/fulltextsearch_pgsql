# Architecture

How the PostgreSQL platform plugs into Nextcloud Full Text Search, and why it is built the way it is.

## Where it sits

```
 Content providers                 Full Text Search app               This app
 (Files, Deck, Bookmarks…)  ──►   (queues, locking, occ,      ──►   PostgreSQLPlatform
  produce IIndexDocument           unified search UI)                implements IFullTextSearchPlatform
                                                                          │
                                                                          ▼
                                                              Nextcloud's own PostgreSQL DB
                                                              table ftspg_<prefix>index
```

The framework calls the platform through `OCP\FullTextSearch\IFullTextSearchPlatform`:

| Method | What happens here |
|---|---|
| `loadPlatform()` | Creates the table if it is missing; never rebuilds an existing table, and throws an error directing to `occ upgrade` or `occ maintenance:repair` if an existing table uses an older schema. |
| `testPlatform()` | Checks the database is PostgreSQL and the schema is in place. |
| `initializeIndex()` | Creates table and indexes (idempotent). |
| `indexDocument()` | Extracts text, then upserts one row. Reports warnings to the runner. |
| `deleteIndexes()` | Deletes rows. |
| `resetIndex($provider)` | Deletes a provider's rows; `all` truncates the table. |
| `searchRequest()` | Runs a search for one provider and fills the `ISearchResult`. |
| `getDocument()` | Rebuilds an `IIndexDocument` from a row (used by `occ fulltextsearch:document:platform` and `occ fulltextsearch:test`). |

## The table

```sql
CREATE TABLE ftspg_oc_index (
  id            bigserial PRIMARY KEY,
  provider_id   text         NOT NULL,
  document_id   text         NOT NULL,
  owner_id      text         NOT NULL DEFAULT '',
  access        text[]       NOT NULL DEFAULT '{}',   -- u:alice, g:sales, c:<circle>, u:__all
  links         text[]       NOT NULL DEFAULT '{}',
  tags, metatags, subtags     text[],
  source, hash (text), modified_time, indexed_at (bigint),
  config        text         NOT NULL,                -- language name the row was indexed with
  title, tags_text, parts (jsonb), parts_text, content, info (jsonb),
  tsv tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector(ftspg_oc_regconfig(config), title),      'A')
     || setweight(to_tsvector(ftspg_oc_regconfig(config), split(title)), 'A')   -- file name parts, see below
     || setweight(to_tsvector(ftspg_oc_regconfig(config), tags_text),  'B')
     || setweight(to_tsvector(ftspg_oc_regconfig(config), parts_text), 'C')
     || setweight(to_tsvector(ftspg_oc_regconfig(config), content),    'D')
  ) STORED,
  title_search text GENERATED ALWAYS AS (lower(title)) STORED,   -- for substring and typo matching
  CONSTRAINT ftspg_oc_index_doc_uniq UNIQUE (provider_id, document_id)
);
-- GIN indexes on tsv, access, metatags, subtags; trigram GIN index on title_search when pg_trgm exists
```

(For Turkish rows each column—including `title_search`—is first passed through `CASE WHEN config = 'turkish' THEN translate(col, 'Iİ', 'ıi') ELSE col END`; see below.)

`config` (and `provider_id`, `document_id`, `owner_id`, `source`, `hash`) are stored as `text` rather than `regconfig` or `varchar(n)` so `pg_upgrade` never rejects the table over `reg*` OID-backed types. Because stored generated columns require `IMMUTABLE` expressions while `text::regconfig` is `STABLE`, `SchemaService` installs an `IMMUTABLE PARALLEL SAFE` SQL wrapper `ftspg_<prefix>regconfig(text) RETURNS pg_catalog.regconfig` (`SELECT $1::pg_catalog.regconfig`), which `DropIndexTable` removes on uninstall after dropping the tables. Every table, wrapper function, `pg_catalog` check, and `pg_trgm` operator/opclass (`<schema>.gin_trgm_ops`, `OPERATOR(<schema>.%)`, `OPERATOR(<schema>.<%)`) is resolved via `pg_catalog` and schema-qualified so queries and `pg_dump` / `pg_restore` work even under `SET search_path = ''` or custom schemas.

### File names

PostgreSQL's text parser reads `rapor_2025_final.pdf` as a single "host" token, so `final` or `2025` would never match it. The title is therefore indexed twice: as written, and with `regexp_replace` splitting it at punctuation (`_ . - / + ~ , ; : ( ) [ ] { }`) and at letter/digit boundaries (`IMG20250412` → `IMG 20250412`). `TsQueryBuilder` splits search words the same way and matches either the whole word or its parts in sequence. The whole form keeps host names and e-mail addresses in document text searchable.

### Schema versions

The generated columns' definition version is stored as a comment on `tsv` (`ftspg schema 3`). `loadPlatform()` creates a missing table on first load, but refuses to rebuild an existing table with an older marker—throwing an error directing the administrator to run `occ upgrade` or `occ maintenance:repair`. When `CreateIndexTable` sees an outdated existing table, it prints the indexed document count and a table-lock notice before calling `SchemaService::ensureSchema()`.

`ensureSchema()` keeps `CREATE EXTENSION IF NOT EXISTS pg_trgm` outside any transaction (so a permission error never aborts the rebuild), then opens a transaction (or a `SAVEPOINT` inside a caller transaction), takes `pg_advisory_xact_lock(hashtext('fulltextsearch_pgsql'), hashtext(<table>))`, and re-checks `isCurrent()` once the lock is held so concurrent callers never rebuild twice. When outdated, it drops `tsv` and `title_search`, alters any non-`text` identifier/config columns and re-adds the generated columns in a single `ALTER TABLE`, updates the comment, recreates the indexes and `ftspg_<prefix>words`, and runs `ANALYZE` atomically; if anything fails, the transaction rolls back with existing columns and rows intact. If the marker is already current, it still restores any missing `ftspg_<prefix>regconfig(text)` function, indexes, or words table without rewriting `tsv`. Recomputing `tsv` locks the table while it runs (about 52 s on the 100,000-document synthetic index) and requires no re-indexing; on large indexes, upgrade during a quiet period.

### Why raw SQL and an unprefixed table name

Nextcloud manages schemas through Doctrine, and Doctrine has no mapping for `tsvector` or `text[]`. Nextcloud introspects **every** table that starts with its table prefix whenever any app runs a migration. A prefixed table with these columns would make all of those migrations fail with *"Unknown database type tsvector requested"*.

So the table is created with raw SQL by a repair step and named `ftspg_` + prefix + `index`, which Nextcloud's schema filter skips. The app also drops `oc_fts_pgsql_index`, the table version 1.0.0 tried to create, for the same reason.

### Why a generated column

The search vector is always consistent with the stored text, a single `INSERT … ON CONFLICT DO UPDATE` writes a document atomically, and weights come for free. Storing `config` per row keeps old rows valid if the language setting changes, until they are reindexed, and lets each document carry its own language when several are configured.

### Several languages

`IndexService` asks `LanguageDetector` for the language whenever content is indexed, and leaves `config` unchanged on metadata-only updates. The detector runs one statement: `ts_debug(cfg, sample)` for each configured `cfg` over the first 2,000 characters, counting word tokens whose dictionary returned no lexeme (stop words). The winner needs at least 2 and 1.5× the runner-up; otherwise the first language is used.

`SearchService` compiles the query once per language with `TsQueryBuilder` and ORs the branches, each guarded by the rows' `text` language name: `d.config = 'english' AND d.tsv @@ to_tsquery('english', …)`; the first language's branch takes `d.config <> ALL (other languages)`, which includes rows indexed in a language no longer configured. Rank queries are computed once in the `q` CTE and picked per row with a `CASE` on `d.config`, and `ts_headline` receives `m.config::pg_catalog.regconfig`. Each branch is a GIN-indexable `@@`, so PostgreSQL combines them with a BitmapOr. With one language the SQL is the same as before.

## Indexing

1. The framework hands over an `IIndexDocument` whose `IIndex` status says what changed.
2. If only metadata changed (`INDEX_META` without `INDEX_CONTENT` or `INDEX_PARTS`), the stored content and parts are kept: a new share does not wipe the text. When `typo_correction` is enabled, `VocabularyService` indexes words only from `title` and `tags_text` without re-scanning stored `content` or `parts_text`.
3. Otherwise `ContentExtractor` produces text:
   - not encoded → used as is; markup is stripped only when `looksLikeMarkup()` detects HTML, XML, or SVG (leading `<!DOCTYPE`, `<html`, `<?xml`, or `<svg` after optional BOM/whitespace, a matching file extension, or for un-encoded content and parts a closing HTML tag such as `</p>` or `<br>`). Block-level tags become spaces before `strip_tags()`, while plain text and comments keep angle brackets;
   - base64 → decoded, then by magic bytes: `%PDF-` → `pdftotext` (`pdftotext_path` is `occ`-only, rejected from web settings with HTTP 400, and validated on save and runtime for basename `pdftotext`, executable bit, and `-v` output), or the bundled parser when it is missing or fails (`pdf_extractor`), with size and `memory_limit` guards and its PHP warnings kept out of the log; `PK\x03\x04` → zip (`OfficeExtractor`), reading `content.xml` (with start breaks on `annotation` and `note`) and `styles.xml` (headers and footers) for ODF, or body, footnotes/endnotes, headers/footers, comments, diagrams, shared strings, sheet names, sheets, and slides/notes for OOXML, stopping at 32 MB per entry, 128 MB uncompressed XML in total, or 2,000 matching entries with a partial-index warning; `\xD0\xCF\x11\xE0\xA1\xB1\x1A\xE1` → Office 97–2003 via `catdoc`, `xls2csv`, or `catppt`; text-like → UTF-8 / UTF-16 / Windows-1254 (also checked with `looksLikeMarkup()`); other binaries → no content plus a warning. External extraction tools (`runTool()`) drain `stdout` and `stderr` concurrently via `stream_select()` (`stderr` capped at 64 KB) and terminate (`SIGTERM`, then `SIGKILL` after a grace period) any process still open when the 60 s timeout or output limit fires, while preserving exit codes on normal EOF;
   - Result is valid UTF-8, has no NUL bytes, whitespace is collapsed, `content` and combined `parts_text` are each capped at `max_content_size` bytes on a character boundary, `tags_text` is capped at 64 KB, `info` has NUL bytes stripped recursively, and tags/links are sanitized.
4. One upsert writes the row. It retries only on `SQLSTATE 54000` (the 1 MB `tsvector` limit); any other error is rethrown immediately so the stored row stays untouched. On `54000`, it degrades through a five-step ladder and stops at the first attempt that fits (recording a warning naming what was cut): `content` halved → `content` quartered → `content` dropped → `parts` cut to 64 KB → `tags` cut to 16 KB and `title` cut to 4,000 characters. Inside a caller's transaction, each attempt is wrapped in a PostgreSQL `SAVEPOINT` so a failed `54000` attempt does not abort the outer transaction.

## Access control

Document access becomes an array of tokens: the owner and shared users as `u:<uid>` (`o:__all` when the owner account itself is literally named `__all`), groups as `g:<gid>`, circles as `c:<id>`, and `u:__all` for public documents. At search time the framework passes an `IDocumentAccess` with the viewer's id, groups and circles, which becomes the same kind of tokens (`o:__all` is granted only when the viewer is `__all`). A row is visible when the arrays overlap:

```sql
WHERE d.access && '{u:alice,u:__all,g:sales,c:team1}'::text[]
```

That is a single GIN-indexed test. Share links are stored for `getDocument()` but never grant search access. An empty viewer id returns no results.

## Searching

`TsQueryBuilder` follows the framework's query contract (verified by `occ fulltextsearch:test`):

| Input | Meaning | tsquery |
|---|---|---|
| `word` | optional, prefix | `to_tsquery(cfg, '''word'':*')` |
| `+word` | required, prefix | same, ANDed |
| `-word` | excluded, exact | `!! to_tsquery(cfg, '''word''')` |
| `"a b"` / `+"a b"` / `-"a b"` | phrase | `phraseto_tsquery(cfg, 'a b')` |

User text first goes through `cleanInput()` to scrub invalid UTF-8 and strip NUL and non-whitespace control characters (preserving tabs and newlines), and is always passed as a bound parameter quoted as a `tsquery` literal, so neither SQL nor tsquery operators can be injected. Three expressions are built:

- **match**: required terms ANDed (or, if there are none, optional terms ORed), minus exclusions, guarded by `numnode(rank) > 0` so a search made only of stopwords returns nothing instead of matching the whole index;
- **rank**: every positive term, for `ts_rank_cd`, and each positive term on its own for IDF weighting (below);
- **all**: every positive term ANDed. Rows matching it sort first, so precise matches are never buried under partial ones.

Required terms, phrases, and `all` predicates wrap each term in `(numnode(ts) = 0 OR predicate)` so stopwords (`numnode = 0`) are skipped rather than forcing an `AND` to false (falling back to optional terms if every required term is a stopword); because `numnode()` receives bound constants, PostgreSQL folds it at planning time and keeps using the GIN index.

The query pages inside a subquery and computes `count(*) OVER ()` for the total; when a page past the end (`page > 1`) returns no rows, `fullTextCount()` runs once so `total` stays accurate instead of dropping to zero. `ts_headline` then runs only on the returned page. Excerpts are plain text (no markup), split into fragments.

### Query planning

The index table's heap is small: titles, arrays and pointers, with every body and search vector stored out of line (TOAST). PostgreSQL's cost model sees a cheap heap, charges almost nothing for evaluating `tsv @@ query` on a row (for a TOASTed vector it means fetching and decompressing it), and overestimates GIN scans. After `ANALYZE` it therefore preferred reading every row the user may see, sequentially or through the access index, and testing each vector: 1.3 s instead of 0.3 s for 12,000 matches among 90,000 visible documents on 100,000, 61 ms instead of 8 ms on 4,000.

Each search now picks where it starts:

- **From the full-text index** (the usual case). Every filter (provider, access, tags, `since`, regex/wildcard) is written as `(condition) IS TRUE`: the same rows, but no index can serve it, so the GIN index is the only way in. Filters then run on the small heap row, which is cheap.
- **From the filters**, when the planner estimates they select fewer than a tenth as many rows as the words, as for a provider with a few documents or a user with few files: testing those few vectors beats visiting every document that contains a common word (160 ms instead of 640 ms for 40 documents against 90,000 with the word). The match condition is then written as `IS TRUE` instead.

Both estimates are planning-only `EXPLAIN`s, about a millisecond each. The search's statements run in a transaction of their own (`withSearchPlanning()`) using transaction-local `set_config(..., true)` for `enable_seqscan` off (a sequential scan stays possible as a last resort), `random_page_cost` at most 1.1 (the usual value for SSDs instead of 4 for spinning disks; a server configured lower keeps its value), `jit` off (before PostgreSQL 18, a disabled plan type adds a huge constant to plan costs, enough to trigger JIT compilation), `pg_trgm.similarity_threshold` (`0.2` when `pg_trgm` is installed), and `statement_timeout` (`search_timeout`, default 10 s; 0 disables) when the search owns its transaction. Inside a caller's transaction, previous planner settings are read and restored inside `try` without setting `statement_timeout` or leaving the transaction aborted on failure; when owning the transaction, reading and applying settings both sit inside `try` so any failure rolls back cleanly. `searchRequest()` catches `SQLSTATE 57014` (returning empty results with `timedOut` set) and `SQLSTATE 2201B` (returning empty results). Tests replay the search's own statements with `EXPLAIN` to check which index each plan starts from.

### Excerpts

`ts_headline` tokenizes all the text it is given: 70–90 ms for a 500 KB document, so a page of long results spent over a second on excerpts alone. Excerpts come from `content` followed by `parts_text` (joined by a space when both exist). Inner subqueries project `d.content` and `d.parts_text` as separate columns without concatenating them, avoiding detoasting non-page rows. On the returned page, `excerptSource()` runs in a `CROSS JOIN LATERAL` behind `OFFSET 0`, checks `octet_length(m.content) + octet_length(m.parts_text) > 10000` without decompressing, and materializes the joined text once; longer texts are excerpted from a 10,000-character window starting 500 characters before the first match (earliest lowercased match of any typed word or `querytree()` lexeme, preferring a word start, or the start when only the title matched). On 20 results of 550 KB, excerpts take 280 ms instead of 1.5 s.

For Turkish rows, `ts_headline` sees the text with `I→ı`, `İ→i` applied, like the indexed vector, otherwise `ISPARTA` would lowercase to `isparta` and never match. Each fragment is then copied back from the original text at the same position (the mapping is one character for one character), so excerpts show the text as written.

### Filters and limited fields

The Files app's search options arrive as request fields, interpreted as the Elasticsearch platform does:

- **Regex and wildcard filters** (*filter by extension* is the regex group `[['title' => '.*\.pdf']]`): entries of a group are ORed, groups are ANDed, and a pattern must match the whole `title` or `content`, ignoring case (`~*` with `^(?:…)$`; wildcards `*` and `?` become `ILIKE`). Patterns over 256 bytes, containing NUL or invalid UTF-8, rejected by PCRE, or using constructs PostgreSQL reads differently or expensively (`\K`, `\Q…\E`, `\b`, backreferences `\1`–`\9`/`\k`/`\g`, named or atomic groups, inline flags, possessive quantifiers, PCRE control verbs `(*...)`, quantified lookaheads, repetition counts above 255, or bounded expansion cost above 4096) match nothing instead of failing the statement. So does a field without a column.
- **Simple queries** (`ISearchRequest::getSimpleQueries()`): keyword, array, integer (`=`, `>=`, `>`, `<=`, `<`), boolean, full-text, wildcard, and regex comparisons apply to `info` keys and known document columns (`title`, `content`, `source`, `hash`, `owner`, `provider`, `document_id`, `modified_time` / `lastModified`, `tags`, `metatags`, `subtags`, `links`, `parts.*`). Wildcard and regex comparisons enforce the same 256-byte, UTF-8/NUL, and regex portability rules as regex/wildcard filters; unknown, type-mismatched, or internal/access fields match nothing.
- **Limit fields** (*search in file name / content*): `title`, `tags`, `parts.*` and `content` map to the vector weights A, B, C and D. Words carry them as tsquery weights (`'rapor':*A`), still served by the GIN index with a recheck; phrases, which `phraseto_tsquery` cannot label, are rechecked against `ts_filter(tsv, '{a}')`; exclusions only exclude within the limited fields. Title substring and title similarity matching only run when titles are searched. A limit naming no indexed field finds nothing.

### Ranking several words by rarity

`ts_rank_cd` counts occurrences and weights them by field (title A, tags B, parts C, body D), but it has no idea how common a word is. In `invoice kırklareli`, a document mentioning *invoice* twice in its body outranks the one document mentioning *Kırklareli* once, although nearly every document says *invoice*. With two to eight positive terms (words or phrases), each one is scored separately and weighted by BM25's inverse document frequency:

```
idf_i = ln(1 + (N - df_i + 0.5) / (df_i + 0.5))
rank  = Σ idf_i · ts_rank_cd(tsv, term_i, 32) / Σ idf_i
```

Normalisation 32 maps each term's weighted occurrence count *c* to *c* / (*c* + 1), a saturating term frequency like BM25's, and the weighted mean keeps `rank` between 0 and 1. Rows containing every term still sort first (`all_match`); the IDF rank orders within that group and among partial matches. Field weights still apply inside each term's score, so a common word in a title can still beat a rare word in body text, as it would with BM25F.

**Frequencies.** Before the search, one statement counts each term's documents with its own subquery: the term's `@@` in each language branch plus the search filters (provider, access tokens, tags, `since`). The GIN indexes answer those conditions exactly, so rows are counted without reading their tsvector; one scan with a `FILTER` per term would detoast every match once per term, six times slower on long documents. Only documents the viewer can open are counted, so ranking reveals nothing about other users' documents.

- Counting stops at 10,000 matches. For a term that common, the planner's estimate (`EXPLAIN (FORMAT JSON)` of the same subquery) is used instead: `ANALYZE` keeps statistics on the most common lexemes, so the estimate is within a few percent for frequent words, and exact counts are spent on rare words, where they matter.
- **N** is `pg_class.reltuples` for the index table, or an exact `count(*)` below 10,000 rows. Counting the viewer's visible documents on every keystroke would cost more than the search. When df is much smaller than N, the difference between two weights is ln(df_j / df_i) whatever N is, so the estimate barely matters; `max(N, df)` keeps the logarithm defined if statistics are stale.
- A term no visible document contains (a stopword, an unknown word) gets no weight. If fewer than two terms remain, or there is one positive term or more than eight, the single `ts_rank_cd` over the whole query is used, exactly as before: with one term IDF cannot change the order.
- Typo alternatives and accent variants are part of their word's tsquery, so they count towards that word's frequency.

The weights are bound into the search as numbers rather than computed in a CTE of the same statement: a second reference to the `q` CTE would materialise it and rule out the parallel scan PostgreSQL uses for large result sets.

**Query shape.** Each extra term costs one more `ts_rank_cd` per matching row. Costed into the scan, that makes PostgreSQL prefer a parallel sequential scan even for a few thousand matches, which tests every row's tsvector and is slower than the bitmap scan of the GIN index. So when the terms' frequencies add up to less than a quarter of the index, the matching scan sits in an `OFFSET 0` subquery that is planned as before, and ranking happens above it. Above that share, PostgreSQL scans in parallel anyway, as it did before, and the unfenced query lets the workers rank.

**Cost**, measured on 100,000 synthetic documents (300 words each, every 20th 8,000 words) with PostgreSQL 16, median of 5:

| Search | Matches | Before | After |
|---|---|---|---|
| one word | 195 / 90,000 | 10 ms / 1.5 s | unchanged |
| two words, mid frequency | 9,000–12,000 | 140–215 ms | 175–320 ms |
| three words, mid frequency | 7,000 | 115 ms | 150–210 ms |
| two or three words, one in 90% of documents | 90,000 | 1.2–1.5 s | 1.3–1.7 s |

On instances where searches match a few hundred documents, the difference is a few milliseconds.

With `pg_trgm` available, each plain search word of three or more characters can also be satisfied by `title_search LIKE '%word%'`, served by the trigram index. The planner combines it with the `tsv` index in one bitmap scan. Stopwords are excluded with `numnode(to_tsquery(…)) > 0`, which PostgreSQL evaluates once at planning time. Substring-only matches have no full-text rank, so they sort after real word matches.

If the exact search returns `total === 0` on any page, `plainWordsOnly` is true (no `+`, `-`, or phrase operators), and `pg_trgm` is available, titles are searched with `word_similarity` (`<%`, GIN-indexed) using `OFFSET` (and `titleSimilarityCount()` when a past-end page returns no rows), excerpting `left()` across `content` and `parts_text`.

## Typo correction

A second table, `ftspg_<prefix>words`, holds every distinct word in the index: lowercase surface forms (`word text COLLATE "C" PRIMARY KEY`, using the `simple` text search configuration so there is no stemming), letters only, 3–40 characters. It has a `folded` generated column (`COLLATE "C"`) with accents removed (`çalışma` → `calisma`, via `translate()` with the same character lists as `Tools\Fold` in PHP), a b-tree index on `folded` in the `C` collation so `LIKE 'prefix%'` is indexed, and a trigram index on `folded` when `pg_trgm` exists.

**Maintenance.** After each document is stored (when `typo_correction` is enabled), one `INSERT … SELECT … ON CONFLICT DO NOTHING` adds its words, computed inside PostgreSQL and inserted in sorted order so concurrent indexers cannot deadlock; metadata-only updates (`INDEX_META` without content or parts) read only `title` and `tags_text`. `CreateIndexTable::fillVocabulary()` also skips work when `typo_correction` is disabled. Words are never removed one by one; `occ fulltextsearch_pgsql:vocabulary --rebuild` takes `pg_advisory_xact_lock`, pages documents in keyset windows (`id > ? ORDER BY id LIMIT n` bounded by `id <= nextId`) into a shadow table with indexes and `ANALYZE`, and swaps it into place by rename at commit so typo and accent corrections keep working uninterrupted during a rebuild (any words written to the previous table by concurrent indexers while the shadow table is building are picked up on the next rebuild). `resetIndex('all')` empties the table.

**At search time**, `SearchService::search()` builds viewer access and search filters (`filters()`) first and supplies a batched `EXISTS` probe (`vocabularyProbes()`) to `VocabularyService::alternatives()`. For each plain positive word (exclusions and phrases are left alone):

1. *Accent variants*: up to 50 vocabulary candidates with the same folded form, or for 4+ letters the same folded prefix, that don't already start with what was typed (shortest first) are checked for visibility in the viewer's filtered documents before deduplicating prefix-covered variants and keeping at most three.
2. *Spelling corrections*, run in a second pass only on page 1 when the uncorrected search returned fewer results than the requested page size (`< size`), for 4+ letter words that have no visible accent variants, are not stopwords (`numnode = 0` in any configured language), have at least one prefix entry in `ftspg_<prefix>words`, and prefix-match no document visible to the viewer under active filters: trigram similarity on `folded` (threshold `0.2`, set transaction-locally in `withSearchPlanning()`) shortlists 50 candidates within ±1–2 letters of length. An optimal-string-alignment edit distance, where swapping adjacent letters counts as one edit, keeps those within 1 edit (2 for 7+ letters); visible candidates are selected before ranking and keeping at most two.

Alternatives are ORed into the word's tsquery as prefix terms (`('rpaor':*) | ('rapor':*)`), so they count towards "all words" ranking and required `+words`, and the original word still matches; if the typed word is a stopword in one configured language (`numnode = 0`), that language branch stays empty even when alternatives exist in another language.

**Viewer-scoped isolation.** Although `ftspg_<prefix>words` is a shared candidate table, every visibility check and candidate shortlist is scoped to documents the searching viewer can open under the active search filters (`vocabularyProbes()` runs one batched `EXISTS` query combining `filters()`, viewer access tokens, active language `tsv` branches via `wordTsQuery()`, and unstemmed `'simple'` surface checks matching `insertSql()` — `w.lexeme ~ '^[[:alpha:]]{3,40}$' AND starts_with(w.lexeme, ?)` on prefix checks). Because inaccessible or filtered-out documents are excluded before deduplication, edit-distance ranking, and truncation, words in other users' documents can never trigger, suppress, supply, or crowd out alternatives.

## Turkish dotted and dotless I

PostgreSQL lowercases with the database's `LC_CTYPE`. Unless that is `tr_TR`, `I` lowercases to `i`, which is wrong for Turkish (`ı`), so `ISPARTA` would index as `isparta` while users type `ısparta`, and uppercase text would miss its lowercase forms. For rows with the `turkish` configuration the generated column applies `translate(text, 'Iİ', 'ıi')` before `to_tsvector`, and `TsQueryBuilder` applies the same mapping to the query. Both sides agree regardless of the database locale.
